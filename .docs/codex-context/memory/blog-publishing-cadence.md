> 历史记录：版本、技术栈与完成状态以现行 [AGENTS.md](../../../AGENTS.md)、项目文档和 Git 为准。历史授权不自动成为当前任务授权。

发布第一篇文章（宝塔面板 SSL 证书自托管实战）后，逐项确认了以下发文正反馈计划：

- **分类**：封顶 AI / 知识（技术工程类通用知识笔记）/ 读书 三类，对应 `content.config.ts` 的 `tags` 字段。当前不加 zod enum 校验，先靠手写规范；如果后续出现标签拼写漂移（参考 badges 系统吃过的"连载中"多一个空格变成两个标签的教训），再回头补 schema 约束。
- **节奏**：每周一篇，作为试运行节奏。用户明确知道每周可投入时间波动很大，我的建议是月度保底 + 弹性节奏，用户否决了这个建议，选择先按固定周频跑——这是用户的决定，不是双方达成一致的推荐项。
- **反馈来源**：暂不引入访问分析或评论区等技术设施，第一阶段反馈来自发布后的社交分享互动、私聊反馈等定性信号。
- **复盘检查点**：累计发布 6-8 篇后，回头评估是否需要加访问分析（如自托管 Plausible/Umami）或评论区（如 giscus），以及每周一篇的节奏是否可持续。
- **选题 backlog**：用户用站外工具（Notion/本地笔记）管理，不在本项目落地，不需要复用项目的 GitHub Issues 机制。

Why：用户希望"持续输出倒逼学习"形成正循环（见全局 AGENTS.md 的「学习方法论」一节），但博客系统本身零反馈基础设施，需要先有一个明确的起步节奏和复盘节点，避免无限期空转或过早引入不必要的技术复杂度。

How to apply：往后新建文章时，`tags` 优先从 AI/知识/读书 三者中选（拼写要准）；累计发布篇数接近 6-8 篇时主动提醒该做复盘；讨论博客技术设施（分析/评论）时，先确认是否已到复盘检查点，避免提前引入。
