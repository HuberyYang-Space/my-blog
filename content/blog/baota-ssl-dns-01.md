## 「起因」

本文记录我用 acme.sh 在服务器上实现SSL自托管的完整操作过程，希望能帮你省点时间。

事情是这样的：我的服务器上部署了很多站点，为了省点米，我一直申请免费的自签证书。能用，但最大的问题是：有效期短，每个月一到期就得手动重新申请证书、替换证书文件，再回宝塔面板里重新配置一遍。站点一多，这套流程每个月都要跑一次，秉承着“懒是第一生产力”的原则，这样重复性的工作我肯定是不能接受的，于是把它变成自动化，从此实现 SSL 自由。

## 「为什么要自托管证书」

多数云厂商和 CDN 也提供免费证书托管，也能自动续期，为什么不干脆用现成的，非要自己折腾一套？三个具体原因：

1. 通配符证书（`*.example.com`）在很多免费额度里有限制或收费，站点子域名一多就绕不开这笔成本。
2. 证书和 CDN、负载均衡强绑定，一旦想换服务商，证书链就得跟着重建，等于把自己焊死在当前厂商上。
3. 自己控制签发和续期链路，出问题时日志和排查路径都在自己手里，完全自主。

反过来说，如果你的站点简单，就一个主域名，也不打算换服务商，云厂商托管证书完全够用，也可以不折腾。

## 「操作环境」

以下是我的服务器环境，供参考，你可以在自己的服务器上按需调整。

- 操作系统：OpenCloudOS 9.6（腾讯云服务器）
- 宝塔 Linux 面板（BT-Panel）
- Nginx 1.27.4

## 「背景知识：ACME 协议和两种验证方式」

Let's Encrypt 免费签发的是域名验证型证书（DV），只证明“这个域名的控制权在你手上”，不验证你的公司身份。ACME（Automatic Certificate Management Environment）就是这套“证明控制权、拿到证书”的自动化协议，v2 版本支持通配符域名和账户级别的多域名管理。

验证域名控制权有两种主流方式。HTTP-01 是在网站根目录放一个指定文件，CA 通过 80 端口访问确认你控制着这个域名，配置简单，但只能验证具体某一个域名。`*.example.com` 底下有无数个可能的子域名，CA 没法针对每一个都去访问一个文件，所以验证不了通配符。DNS-01 是让你在域名的 DNS 记录里加一条指定内容的 TXT 记录，CA 通过查询 DNS 确认你控制着整个域名的解析权，因此天然支持通配符，代价是需要一个能自动读写 DNS 记录的 API。

结论：只需要单个域名的证书，HTTP-01 更省事；只要涉及通配符，DNS-01 就是唯一选择。

## 「为什么选 acme.sh」

acme.sh 是一个纯 Shell 实现的 ACME 客户端，不依赖 Python 环境。它在这条链路里做三件事：调用你配置的 DNS 服务商 API，自动写入 TXT 记录并在验证完成后清理掉；向 Let's Encrypt 发起签发请求；把签发到的证书和私钥落地到本地文件，并注册一个定时任务负责续期。

和 certbot 比，acme.sh 更轻量，没有 Python 依赖链的问题，社区维护的 DNS API 插件覆盖面也更广，主流云厂商基本都有现成插件（比如我用的 `dns_tencent`）。

## 「操作步骤」

### 1. 申请一个只管 DNS 的密钥

这一步很重要：不要直接用主账号密钥。绝大多数教程图省事让你直接填主账号密钥，这个密钥的权限覆盖你整个云账号，而不只是 DNS 解析，是有一定风险的。

首先登录腾讯云控制台（我使用腾讯云，其他云厂商的菜单名不一样，但步骤基本一致）：

1. 登录腾讯云控制台，进入“访问管理”（CAM）。
2. 左侧菜单点“用户” → “用户列表” → “新建用户” → “快速创建”，访问方式选“编程访问”，不要勾“腾讯云控制台访问”，这个子账号以后只用来被 acme.sh 调用，不需要控制台登录，遵循最小权限原则。
3. 授权这一步，搜索并勾选策略 `QcloudDNSPodFullAccess`（云解析 DNS 全读写）。注意不要选成 `QcloudDNSPodReadOnlyAccess`，DNS-01 验证需要 acme.sh 自动新增和清理 TXT 记录，只读权限做不到。
4. 其他选项保持默认，创建完成后进入这个子账号的详情页，点“API 密钥” → “新建密钥”，拿到一对 SecretId / SecretKey。

::warning
**SecretKey 只显示这一次**：腾讯云从 2023 年 11 月 30 日起关闭了创建后再次查看 SecretKey 的入口，弹窗一关，这把 SecretKey 就再也找不回来了，务必保管好。
::

做完这一步，就拿到了一对权限仅限于 DNS 解析、和主账号完全隔离的密钥，不会影响主密钥。

### 2. 安装 acme.sh

登录服务器或者在宝塔面板终端中执行：

```bash
curl https://get.acme.sh | sh -s email=你的邮箱
```

安装成功会在当前用户主目录下生成 `.acme.sh` 文件夹，同时自动把续期任务注册进 crontab。

安装脚本会顺手把一行 `source` 命令写进当前 shell 的 profile（比如 `~/.bashrc`），这样以后才能直接敲 `acme.sh` 而不用输一长串路径。需要重连一次 SSH，或执行：

```bash
source ~/.bashrc
```

用 `acme.sh --version` 确认安装无误，再往下走。

### 3. 设置密钥，发起签发

把第一步拿到的密钥设成环境变量。用 `dns_tencent` 插件时，变量名是固定的两个，在服务器终端执行：

```bash
export Tencent_SecretId="你的 SecretId"
export Tencent_SecretKey="你的 SecretKey"
```

这两行命令只在当前 SSH 会话里生效，关掉终端就没了，不用管，也不必特意写进 `.bashrc` 持久化：acme.sh 签发成功后会自动把这对密钥存进 `~/.acme.sh/account.conf`，以后 crontab 触发的续期是从这个文件里读，不依赖当前 shell（见下文「闭坑指南」）。

::tip
**用的不是腾讯云？** 每个 DNS 插件要求的环境变量名不一样，命名规律都是 `<厂商>_<字段>`。去 acme.sh 官方 GitHub 仓库的 wiki 里找 dnsapi 那一页，每个插件都单独列了自己要设哪几个变量，可以参考操作。
::

设好之后执行：

```bash
acme.sh --issue --dns dns_tencent -d example.com -d '*.example.com'
```

`--dns` 后面换成你对应的插件名（我的是 `dns_tencent`），`-d` 后面是要签的域名，通配符证书就把主域名和 `*.域名` 都列上。

执行后 acme.sh 会自己去调用 DNS 服务商的接口写入并验证 TXT 记录，正常情况下几十秒到几分钟内会返回结果。如果长时间卡住或直接提示失败，打开 `~/.acme.sh/acme.sh.log`，这里的报错信息最完整。常见原因通常是两种。DNS 记录还没生效，不同服务商的 TXT 记录生效延迟不一样，稍等一会儿再重试就好；密钥权限不够，回头检查第一步里子账号授予的是不是 DNS 解析读写权限。日志里如果出现和密钥、鉴权相关的字样，基本可以确定是第二种情况。

### 4. 把证书装到 Nginx 认得的位置

acme.sh 默认只是把证书签下来放进自己的目录，Nginx 并不会自动认得它，还得显式安装一次。路径是你打算存放证书的路径，宝塔面板给每个站点约定好了固定的证书存放路径，直接指过去，不用自己另找地方放：

```bash {2,3}
acme.sh --install-cert -d example.com -d '*.example.com' \
  --key-file /www/server/panel/vhost/cert/example.com/privkey.pem \
  --fullchain-file /www/server/panel/vhost/cert/example.com/fullchain.pem \
  --reloadcmd "systemctl reload nginx"
```

高亮的地方，`example.com` 换成你的域名，`--key-file` 和 `--fullchain-file` 是私钥和证书链最终落地的路径，这个目录宝塔在建站的时候就已经建好了，不需要自己 `mkdir`。如果你没用宝塔管理这台服务器，改成你 Nginx 配置里实际引用的路径即可。`--reloadcmd` 顺带解决了“续期之后要不要手动重载 Nginx”这个问题：以后每次自动续期，acme.sh 都会把这条命令再跑一遍，证书换了、Nginx 也跟着重载，完全自动化。

### 5. 确认自动续期已经注册

安装脚本已经自动把续期任务写进 crontab。在服务器终端执行 `crontab -l` 确认存在类似输出：

```bash
51 14 * * * "/root/.acme.sh"/acme.sh --cron --home "/root/.acme.sh" > /dev/null
```

acme.sh 的续期逻辑是每天检查一次，证书剩余有效期不到 30 天时才真正重新签发，所以这一行每天都会跑，不代表每天都在续期。只要确认“续期任务存在”就好。

### 6. 确认证书真正生效

证书装完不代表 Nginx 已经在用它，这一步要实际去验证。用 `curl -vI https://your-domain.com` 或者浏览器开发者工具查看当前站点证书链，核对证书的签发时间和到期时间是不是跟你刚刚签发的对得上。对得上，才算这次申请真正落地。

### 7. 宝塔管理的站点如何操作

以上 acme.sh 签好的证书躺在服务器某个目录里，宝塔并不知道它的存在，需要手动接上。两种接法，挑一种就行：

- 笨办法但直观：宝塔面板 → 网站 → 对应站点 → SSL → 选“其他证书”，把 acme.sh 装好的证书内容和私钥内容粘贴进去，直接在服务器上 `cat` 出来复制：

  ```bash
  cat /www/server/panel/vhost/cert/example.com/fullchain.pem
  cat /www/server/panel/vhost/cert/example.com/privkey.pem
  ```

  第一条命令的输出粘进“证书内容”，第二条粘进“私钥内容”。

  ::caution
  **证书内容不要漏了证书链**：“证书内容”这一栏要粘的是 `fullchain.pem`，也就是域名证书加上中间证书链拼在一起的完整链条，不是只有域名证书本身。少粘了中间证书链，站点在你自己浏览器里可能看着正常（浏览器会自动补），但部分客户端或旧设备访问时会报证书链不完整。
  ::

- 省心的办法：第 4 步 `--install-cert` 里的 `--key-file` / `--fullchain-file` 就是直接写成宝塔的证书目录，配合 `--reloadcmd`，两边路径本来就已经对上了，不用再额外操作。不放心的话去宝塔面板 → 网站 → 对应站点 → SSL 页面，核对一下当前引用的路径是不是同一个。以后每次续期，证书原地覆盖、Nginx 自动重载，彻底不用再手动碰宝塔面板。

## 「温馨提示」

- 正式域名操作前，先在一个不影响线上业务的测试子域名走一遍完整流程，把踩坑成本降到最低（过来人的经验）。
- 生成 DNS API 密钥的时候，顺手在密钥管理后台的备注栏写清楚用途，比如“仅用于某域名 acme.sh 续期”，半年后自己回头看还认得这把钥匙是干什么的。

## 「闭坑指南」

这套流程跑通之后，我顺手检查了一遍自己服务器的实际配置，在 acme.sh 的账户配置文件里翻到一对明文存放的云 API 密钥。这是 acme.sh 用 DNS API 方式签发证书时自己的默认行为，跟用不用宝塔没关系，照着上面的步骤走一遍，绝大多数人都会踩进同一个坑里。

::warning
**API 密钥权限过大**：前面提过，acme.sh 的账户配置文件（`account.conf`）里明文存着 DNS API 的 SecretId 和 SecretKey，这是它的正常工作方式，不是 bug。但如果这对密钥是主账号权限，风险就从“域名解析可能被篡改”放大成“整个云账号可能被接管”，这个风险还是要尽量避免。
::

::note
**相似域名混淆导致重复证书**：用 `acme.sh --list` 查证书清单时，发现列表里同时躺着两个拼写只差一个字母的域名，各自签了一套通配符证书，其中一个完全没有续期记录，说明是很久以前手动签发后被遗忘的。长期用 DNS-01 自动续期就很容易忘记清理这类历史证书，建议定期跑一次 `acme.sh --list`，手动核对每一张证书是不是还在实际使用。
::

::caution
**crontab 任务堆积，续期任务容易被误删**：宝塔面板自己会往 crontab 里塞不少定时任务（日志清理、监控心跳等），acme.sh 的续期任务混在中间，如果哪天手动清理 crontab 图省事直接清空重写，很容易连带把续期任务一起删掉。所以改 crontab 前先 `crontab -l` 看一遍现有内容，养成好习惯。
::

## 「下一步」

如果你成功应用了这套方案，花两分钟做两件事：跑一次 `acme.sh --list`，看看清单里是不是也躺着几张自己都不记得申请过的证书；再去云厂商控制台确认一下你用来做 DNS-01 验证的那对密钥，权限范围是不是被限制在 DNS 解析，而不是主账号级别。

## 「FAQ」

**acme.sh 自动续期失败怎么排查？**
先去 `~/.acme.sh/acme.sh.log` 查详细报错。常见原因是 DNS API 密钥过期或权限被收回、DNS 记录生效延迟超时、以及 crontab 里的续期任务被误删。用 `crontab -l` 确认续期任务还在，是最基础的排查步骤。

**DNS-01 和 HTTP-01 验证方式该怎么选？**
只要涉及通配符证书，只能用 DNS-01。如果只有单个明确域名、不需要通配符，HTTP-01 配置更简单，不需要额外申请 DNS API 密钥。

**acme.sh 和 certbot 该选哪个？**
acme.sh 纯 Shell 实现，没有 Python 依赖负担，装起来更轻量。如果你的服务器本来就是重度 Python 环境、或者团队更熟悉 certbot 的操作习惯，用 certbot 也没问题。两者都不依赖宝塔，选哪个纯粹看个人习惯，签发的证书本质没区别。

**通配符证书和多域名证书有什么区别？**
通配符证书（`*.example.com`）覆盖该域名下所有一级子域名，适合子域名会动态增加的场景。多域名证书（SAN 证书）是把几个明确写死的域名签到同一张证书里，域名列表变化时需要重新签发，适合子域名数量固定、可预期的场景。
