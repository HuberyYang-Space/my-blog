这个效果我提交了两次，中间连着三轮「验证通过」全部作废。从头到尾，构建没有红过一次。

五个坑，没有一个报错。画布被悄悄横向压扁、文字整体上移三四个像素、切换主题之后字变成纯黑（暗色主题下就是消失）。它们的表现是同一种：页面还在，只是看着有点怪，而怪在哪里得盯很久才说得出来。

最难受的一个是我自己写的守卫。那条断言写完之后一次都没红过，我当时以为这说明这里已经守住了。

下面把五个坑和三次作废的验证完整写下来。液态特效本身那部分你可以跳着看：shader 代码网上到处都是，真正难的从来不是把它跑起来，是怎么知道它对了。

## 「起因」

在此之前，首页的 `Hubery` 就是一个 `<h1>`：字号 `clamp(2.25rem, 5vw, 3.5rem)`，字重 700，后面跟一个闪烁的下划线光标。它挺好，但它不动。

说实话，效果本身是借口。我想找个由头玩一次 WebGL 和 shader，博客首页正好是自己的地盘，改坏了也只有我自己看见。

真要说想要什么：鼠标划过时，那几个字母像隔着一层被搅动的水，划得越快，颜色分得越开。

::

## 「四个方案是怎么比的」

一开始我把四条路各写了一份，摆在同一个对比页上并排跑，带 FPS 计数和单独开关。

| 方案 | 依赖 | 做法 |
| :--- | :--- | :--- |
| 粒子文本 | 零依赖，Canvas 2D | 文字按 alpha 采样成约 2500 个粒子，鼠标轨迹推开，松手后 spring 归位 |
| **液态扭曲** | `ogl`，约 20 KB gzip | 文字画成贴图，Flowmap 把鼠标速度累积成一张图，shader 按速度偏移采样坐标 |
| CSS 3D 立体字 | 零依赖 | 多层阴影叠出厚度，鼠标控制旋转 |
| three.js 真 3D | `three`，约 170 KB gzip | `TextGeometry` 把字形真的挤出成几何体 |

最后选了液态扭曲。粒子文本效果我一样认可，只是同一个位置放不下两个，它现在还留在仓库里等一个去处。

### 为什么不是 three.js

真挤出的立体字是四个方案里最“厚”的一个，看起来也最唬人。并排跑过之后我把它淘汰了，代价有三道。

第一道成本在字体。`TextGeometry` 吃的是 typeface JSON 格式的字体，而 three 的 npm 包里**没有** `examples/fonts/`（只有 `examples/jsm/`）。想用就得自己准备一套 ttf 到 typeface 的转换流程：找一个 ttf、转出 JSON、丢进 `public/`、页面加载。

转出来的字形和站点正文对不上。站点用的是系统字体栈（macOS 上是 PingFang SC），而 typeface 转换吃的是一个具体的 ttf 文件。你转的是某一个字体，不是“用户机器上那个字体”。首页标题于是成了全站唯一一处用别的字体的地方，并排摆着看的时候，这一点比想象中刺眼。

体积是压垮它的最后一项。`three` 约 170 KB gzip，是 `ogl` 的八倍多。为首页一个单词付这个价，不划算。

这一步不算白走。四个方案在同一个页面上并排跑过、手感都摸过，选液态扭曲才不只是“看参数哪个更轻”。

::tip{title="什么情况下不必折腾 WebGL"}
如果你只想让标题“有点动静”（悬停变色、轻微位移、描边扫光），CSS 那条路就够了，零依赖、零 shader、改起来五分钟。**液态效果的成本不在那 20 KB，在下面那五个坑**，它们全是接一层 canvas 才会有的问题。
::

## 「效果是怎么搭起来的」

三步，就这么多：

1. 把标题用离屏 canvas 画成一张贴图（白字，透明底）
2. `ogl` 的 `Flowmap` 把鼠标轨迹累积成一张速度图，鼠标停下后逐帧消散
3. fragment shader 拿速度去偏移采样坐标：鼠标划过的地方，文字被“推”着流动

Flowmap 那张图有三个通道，分工是关键：**R/G 存 xy 方向的速度，B 存速度长度**。位移吃 R/G，色差强度吃 B。

```glsl
// 三个通道各偏一点,速度越快分得越开
float r = texture2D(tMap, vUv - offset - vec2(chroma, 0.0)).a;
float g = texture2D(tMap, vUv - offset * 1.12).a;
float b = texture2D(tMap, vUv - offset * 1.24 + vec2(chroma, 0.0)).a;
```

分开的好处是：慢慢移只有形变没有色散，快速划才炸开。合在一起的话，“液体”就变成了“果冻”。

贴图上只画白字，颜色在 shader 里用 uniform 现填。这样切主题只需要改一个 uniform。如果改成重画贴图，切换时会因为重新上传纹理闪一帧。

好了，实现部分到此为止。**下面才是这篇文章的正文。**

## 「闭坑指南」

五个坑排在下面。它们的共同点不是“难”，是**你不会知道自己踩了**：没有报错、没有告警、构建照常绿。

### 1. 画布被 reset 悄悄压回容器宽度

现象最戏剧的一个：刷新页面的那一瞬间字是正常的，然后突然变小、并且往左错位。

原因在 `reset.css` 里那条再普通不过的规则：

```css
img,
video,
svg,
canvas {
  max-width: 100%;
}
```

它防的是图片撑破容器，写得没错。问题是这块画布**刻意**比容器宽：文字四周各留了 48px，给流动溢出的笔画。`max-width: 100%` 一上，画布被压回容器宽度，而 `style.height` 是脚本单独设的，不跟着变。

于是纹理被横向压扁，字看起来又小又偏左。

为什么刷新那一瞬是对的？因为那一瞬你看到的还是 DOM 里的真文字。效果接管、涂透明、canvas 显形，是几十毫秒之后的事。

```css
.hero-title canvas {
  /* 这块画布刻意比容器宽,不解除的话被压回去,纹理横向压扁 */
  max-width: none;
}
```

::warning{title="这个坑连 HTML 都不变"}
产物断言在这里完全无能为力：它读的是 HTML，而这个失败发生在运行时的 CSS 计算结果里，HTML 一个字符都不会变。所以它由一条单测直接读 SFC 源码来守，检查 `.hero-title canvas` 的规则里有没有 `max-width: none`。
::

### 2. `textBaseline: 'middle'` 对齐的不是你以为的那个中点

画布上的字要和底下那份 DOM 文字严丝合缝地重叠，差几个像素就能看出来，因为光标还在旁边，参照物是现成的。

我一开始用的是 `textBaseline: 'middle'` + `y = h / 2`，看起来天经地义：把文字摆在画布的垂直中心。

画出来整体上移了三四个像素。

`'middle'` 对齐的是 **em 方块的中点**，而字体的 ascent 与 descent 对那个中点并不对称。这套系统字体实测下来是 **54 : 12**。把一个不对称的东西按“中点”摆进一个盒子，它当然不会落在你想要的地方。

正确的做法是用基线定位：

```ts
const ascent = octx.measureText(text).fontBoundingBoxAscent
octx.textBaseline = 'alphabetic'
octx.fillText(text, PAD_CSS * dpr, PAD_CSS * dpr + ascent)
```

`fontBoundingBoxAscent` 就是字体的 ascent，而浏览器计算 inline 元素外框顶部用的是同一个量。所以「外框顶部往下 ascent」正是 DOM 那份文字的基线所在，两者由此重合。

这不是 canvas 的 bug，是 `'middle'` 的定义如此。**它按定义工作，只是那个定义不是你要的东西。**

### 3. `letter-spacing` 不在 canvas 的 `font` 简写里

标题上有 `-0.02em` 的收紧。`octx.font` 的简写里塞不进 `letter-spacing`，得单独设一次：

```ts
const spacing = Number.parseFloat(cs.letterSpacing)
if (Number.isFinite(spacing))
  octx.letterSpacing = `${spacing * dpr}px`
```

不设的话，画出来的字比 DOM 那份宽出几个像素。而画布宽度是按 DOM 文字量算的，于是紧跟在后面的闪烁光标会压到最后一个字母上。

乘 `dpr` 别忘了：纹理里的字号放大了同样的倍数，间距不跟着放大就对不上。

### 4. 切一次主题，字变成纯黑

这个最隐蔽，也是我最喜欢的一个。

贴图上画白字，颜色由 shader 现填，所以脚本要读一次文字的实际颜色。第一版是从文字元素自己身上读的：

```ts
const match = getComputedStyle(textEl).color.match(/\d+/g)
```

首次构建时它是对的。因为首次构建发生在“涂透明”之前，那时 `.hero-title-word` 还是正常颜色。

而切换主题会触发一次重建。这一次读到的是 `rgba(0, 0, 0, 0)`，因为效果早已接管、文字已经被涂成 `transparent`。正则抓出前三个数字，解析结果是**纯黑**。

亮色主题下你几乎注意不到（本来就是深色字）。暗色主题下，深底黑字等于消失。

修法是从**父元素**读：

```ts
const colorSource = textEl.parentElement ?? textEl
const match = getComputedStyle(colorSource).color.match(/\d+/g)
```

::warning{title="这个坑要满足两个条件才现形"}
必须**切换过一次主题**，而且必须在**暗色**下看。只在亮色主题里开发、或者从头到尾没点过那个切换按钮，它就一直不出现。这类“要凑齐两个条件才现形”的问题，是最容易带着上线的，因为你日常的那条路径永远踩不到它。
::

### 5. `dpr` 在挂载时定死，换个显示器就发虚

`devicePixelRatio` 我一开始在 `onMounted` 里取了一次就存着用。

把窗口从内置屏拖到外接显示器上（两块屏 DPI 不同），画布分辨率就对不上屏幕了，字发虚。

`devicePixelRatio` 没有专门的变化事件。标准做法是给当前值建一个 media query，它失配的那一刻就是 dpr 变了。换到新值之后要**重新建一个**，因为 query 钉死在具体数值上：

```ts
function watchDpr() {
  dprQuery?.removeEventListener('change', onDprChange)
  dprQuery = window.matchMedia(`(resolution: ${window.devicePixelRatio}dppx)`)
  dprQuery.addEventListener('change', onDprChange)
}
```

顺带一提，重建纹理这件事有三个触发源（窗口尺寸、元素尺寸、dpr 变化），一次窗口拖动会连着来几十下。全部走同一个按帧合并的入口。每下都重画一张贴图并重新上传纹理的话，拖动过程会明显卡。

## 「三次作废的『验证通过』」

上面五个坑，最后一个是我在验证方法出问题**之后**才找到的。中间那段是这篇文章里我最想让你看到的部分。

事情是这样的：改完画布的定位逻辑，我去浏览器里验证。做法是打开控制台，按新的算式把理论偏移量算一遍，算出来是 0，正正好好对齐。验证通过。

连着三轮都是这么“通过”的。

后来发现：**浏览器一直在跑缓存里的旧模块。**

磁盘上的文件是新的，`curl` 直接问 dev server 也返回新代码，唯独浏览器加载的还是旧的那一份，`Cmd+Shift+R` 都没换掉。三轮结论全部作废。

### 我验的是算式，不是页面

回过头看，那个“验证”从一开始就不成立。我在控制台里按新算式算了一遍理论值，算出来当然是对的，**因为我验的是那道算式，不是页面**。页面跑的是哪一版代码，这个动作从头到尾没有碰过。

判据是：**你选的那个观测量，能不能区分新旧？** 算式算出来的理论值，新旧代码下都一样，它区分不了任何东西。要么找一个只有新代码才有的可观察行为，要么直接比对浏览器实际加载的模块文本。

### 先确认版本，再开始测

可靠的做法是从 dev server 直接取一次源码，比对里面有没有新代码的标识符：

```bash
curl -s "http://[::1]:3000/_nuxt/@fs/绝对路径/app/components/HeroTitle.vue" | grep fontBoundingBoxAscent
```

注意路径要走 `@fs` 加仓库绝对路径。`/_nuxt/app/components/HeroTitle.vue` 这种写法是 404。

这条命令有两个前提。一是 dev server 在 IPv6 上监听，所以地址是 `[::1]`。二是它返回的是 Vite 转换后的模块文本，grep 的标识符要挑转换后仍然原样保留的，比如变量名、字符串字面量，别挑注释。

### 一轮测不通，先怀疑版本

这是我从这件事里拿走的最实用的一条：**测试结果和预期不符时，第一反应不该是改代码。**

否则你会去“修”一个已经修好的问题。运气差一点，还会把对的代码改坏，因为你的修改基于一个从未被验证过的错误结论。

::caution{title="Claude in Chrome 的隔离环境里，这几样东西不工作"}
如果你也在用 AI 助手驱动浏览器做验证，记下这几个：`ResizeObserver`（连规范要求的首次触发都没有）、`window.dispatchEvent` 派发的事件（到不了页面自己的监听器）、`resize_window`（对最大化或跨屏的窗口无效，`outerWidth` 报 0）。

它们**不报错**，只是安静地什么都不做。拿它们当判断依据，你会得到一个看起来很确定的错误结论。
::

## 「守卫要怎么写才算数」

修完坑，得留下东西防止它们再回来。这一步我也搞砸过一次。

首页标题有一条不变量：**真文字必须留在 `<h1>` 里**。看得见的是盖在上面的 canvas，但撑开布局、能被选中、被屏幕阅读器朗读、出现在静态产物里的，全靠那个没被删掉的 `<span>`。哪天有人把它改成“由 canvas 生成文字”，页面看起来一模一样，搜索引擎拿到的却是个空标题。

所以我加了一条产物断言。第一版是这么写的：

```ts
if (!html.includes('>Hubery<'))
  fail('hero', '首页 <h1> 里的标题文字不见了')
```

它永远不会失败。因为 `<title>Hubery</title>` 里也有 `>Hubery<`。`<h1>` 里的文字全删光，这条断言照样绿。

正确的写法是先定位到那个 span，再比对内容：

```ts
const heroWord = html.match(/class="hero-title-word"[^>]*>([^<]*)</)?.[1]
if (heroWord !== SITE.title)
  fail('hero', `首页 <h1> 里的文字是「${heroWord}」,期望「${SITE.title}」`)
```

**一个永远不会失败的断言，比没有断言更糟。** 没有断言，你至少知道这里没人守着；有一条假的，它占着守卫的位置，还顺便替你把心放下了。

这个问题是靠“故意把 `<h1>` 里的文字删掉，看断言会不会红”发现的。所以：

::tip{title="加了守卫就故意破坏一次"}
守卫不报错，不等于守卫有效。写完一条检查，立刻把它要防的那个东西弄坏一次，确认它真的会红。花不了两分钟，能挡住一整类“看起来守住了”的错觉。
::

还有一件事：**两层守卫管的不是同一件事**。产物断言查 HTML，查得到“文字还在不在”；但第 1 个坑里那条 `max-width: none`，删掉之后 HTML 一个字都不变，产物断言查不到。它由单测直接读 SFC 源码来守。

一个跑在构建产物上，一个跑在源码文本上，都不能省。

## 「什么情况下不必这么做」

这套东西的性价比得算清楚。

**只想要一点动静**：CSS 就够了。上面五个坑一个都不会遇到，它们全都是“往页面上盖一层 canvas”带来的。

**标题是中文**：贴图那条路会更麻烦。中文字体的度量差异比拉丁字体大得多，第 2 个坑的表现会更明显，而且字数一多贴图尺寸就上去了。

**站点没有主题切换**：第 4 个坑整个不存在，因为不会触发重建。

**团队项目**：留下的是一个没有报错兜底的地方。要么把守卫写足（源码一条、产物一条），要么别留给下一个人。

反过来说，如果你的站点就是个人博客、标题是一个拉丁单词、而且你享受折腾这个过程——那就值。我自己是这样。

## 「下一步」

如果你的项目里也有类似的“效果层”（canvas 覆盖、WebGL、CSS 变换叠加），**花两分钟做两件事**：

1. 打开一个你最近改过的效果，**切一次主题**，然后在暗色下再看一遍。第 4 个坑就是这么被抓到的，它平时不出现。
2. 挑一条你写过的断言，**故意把它要防的东西弄坏**，看它会不会红。如果它照样绿，你刚刚发现了一条假守卫。

我那条断言在仓库里躺了一阵才被发现是假的。发现它的不是代码审查，是一次随手的破坏演练。

## 「FAQ」

**为什么不用 `mouseenter` / `mouseleave` 触发效果？**

事件是个开关：鼠标一压线，整块字突然开始流动，那一下很突兀。改成“鼠标到文字外框的最短距离”做渐变，靠近这个过程本身就成了效果的一部分。

**shader 写错了会怎样？**

canvas 一片空白，页面没有任何报错，构建照常成功。**shader 编译失败是静默的**。改完一定要在浏览器里实际看一眼，别只看构建结果。

**为什么闪烁的光标不画进贴图？**

贴图是重建时才更新的静态图。光标画进去就会变成一根定住不动的下划线。它走默认插槽，留在 DOM 里照常渲染。同理，“涂透明”这个操作只作用于 `.hero-title-word`，包住插槽的话光标直接消失。

**性能怎么样？**

单个全屏三角形加一张贴图，逐帧只跑一遍 Flowmap 更新和一次 draw call。真正需要防的是重建纹理：它要重画一张离屏 canvas 并重新上传，一次窗口拖动能触发几十次，所以三个触发源合并成一个按帧节流的入口。
