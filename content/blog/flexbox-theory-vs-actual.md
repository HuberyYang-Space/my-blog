容器宽 200px，三个盒子横着排，不换行。每个盒子里都有一整块 120px 宽的内容，中间留两个 12px 的间隔。扣掉间隔，三个盒子可以分 176px。起点一样，`flex-shrink` 也都是 1，每个分到 58.7px 左右，算起来刚好。

可你看图里的 B。斜纹手柄已经是容器的右边界了，B 还有半截留在外头，C 整个都出去了。明细表里三个盒子的实际宽度全是 120px。

## 「少算的那一步」

先算三个盒子要让出多少地方。这里没单设 `width`，`flex-basis: auto` 取到的起始宽度都是 120px。

```text
三个盒子加两个间隔，一共要 3 × 120 + 2 × 12 = 384px
容器只有 200px，还得挤出 184px
每个盒子的收缩权重 = flex-shrink × 起始宽度 = 1 × 120
三个权重相同，各让出 184 ÷ 3 ≈ 61.3px
分摊后的宽度 = 120 − 61.3 ≈ 58.7px
```

算到 58.7px，还差一个问题：**这个盒子真能缩到那么窄吗？**

横向 flex 布局里，子元素的 `min-width` 默认为 `auto`。图中这几个盒子都保留了默认的可见溢出，内容又是一整块，没地方断开，在这里自动最小宽度就是 120px。每个盒子分摊完都碰到了这个下限，定在 120px。三个都缩不动，多出来的 184px 只好溢出容器。

这个例子巧在三个盒子一样宽，除以三就算对了分摊。要是起始宽度不同，哪怕 `flex-shrink` 都是 1，也要按各自的 `shrink × basis` 分，起始宽的那个要多让一点。换成有富余空间的一行，则看 `flex-grow` 的比例。遇到某个盒子先碰到尺寸限制，就把它固定下来，剩下的盒子再分。这也是规范里为什么会有“冻结”那一步。[Flexbox 规范中的弹性长度计算](https://www.w3.org/TR/css-flexbox-1/#resolve-flexible-lengths)

如果你自己项目里正好有一行被长内容撑开，可以在开发者工具里只给那个子元素加 `min-width: 0`。它现在能缩了，里面的内容要换行、截断还是允许溢出，再按实际需要处理。主轴竖着走时，对应的是 `min-height: 0`。布局原本好好的，就不用挨个补。

## 「所以我在明细表里放了两列」

学 `justify-content` 的时候，切一下按钮看盒子往哪边靠就够了，MDN 或 Flexbox Froggy 都挺直观。我做项目时更常卡在尺寸上。比如同一行的子元素都写了 `flex: 1`，为什么左栏偏偏比右栏宽？开发者工具能告诉我它最后多宽，我还想知道它在哪一步多占了空间。为这个问题，我花了一个月、提交了 141 次，做出这张明细表。

左边是一组纯函数。它取 basis，按 `order` 排列，需要换行时分行，每行扣掉 basis 和 gap，再做伸缩分摊。百分比 basis 在主轴尺寸确定时按容器算。这套推导把收缩下限简化成 0，刻意留出了自动最小尺寸的影响。右边就老老实实摆 DOM 元素，交给浏览器用 CSS 排，排完去量。示例里左边的 58.7px 和右边的 120px，各有来处。

两列一比，可以逐个盒子解释。图里是它自己停在内容宽度上，表里会标这条：

```text
⚠ min-width:auto 撑住了内容固有尺寸，收缩到此为止
```

也有被邻居连累的。假如同一行只有 A 被内容撑住，多占的空间还得从 B、C 身上挤，B、C 就可能比理论值更小。诊断会指出是哪一个盒子多占了宽度。如果连换行的位置都变了，要先核对两边每行有哪些盒子。实在对不上已知原因，表里就写没能归因。

这样也比较好理解 `flex: 1` 和 `flex: auto`。在主轴宽度确定的容器里，浏览器通常把前者展开为 `1 1 0%`，可以从零开始按 grow 分；后者是 `1 1 auto`，没指定宽度时，各自先按内容占位，再分余量。两种写法都还要过最小尺寸那一关，同样写 `flex: 1` 也可能分不匀。

## 「闭坑指南」

要敢把右边那列叫“实际值”，我得先知道自己到底量了什么。推导这边我拿一千多个随机场景和真实 Chrome 对拍，在那批对拍条件下数值对上了。测量这边，整数宽度的例子跑得再多，也找不出第二条里的半个像素。

### 1. 盒子动画走到一半，该读哪个宽度

我给位置变化加了 GSAP Flip 过渡。布局已经排到终点，Flip 再用 `transform` 把盒子从旧位置移过去。这时候读 `getBoundingClientRect()`，拿到的是眼睛看到的动画中间态，明细表里的数字也跟着跑。

我需要的是布局给出的值。尺寸从计算样式里读，位置用 `offsetLeft` 和 `offsetTop`。`ResizeObserver` 就负责通知“该重新量了”，和其他触发采样的地方共用同一种读法。

### 2. 17.5px 怎么就读成了 18px

`offsetWidth` 也能避开 transform，可它返回整数。我遇到一个实际宽 17.5px 的盒子，读出来是 18px，跟推导值一比差了 0.505px。诊断原本允许 0.5px 的亚像素偏差，这下刚好越线，凭空多出一条警告。

只用整数做演示，压根看不出这毛病。等我专门排出带小数的宽度，一行里几次取整的偏差叠起来，连整行的标记都跟着错了。这就是上面读计算样式时，我特意要留下小数的原因。

### 3. 我只想给盒子描个边

给每个盒子加 `border`，在演示区看着挺清楚。麻烦在于我的推导没算这圈装饰，导出的 CSS 里也没有它。描边占了布局空间，三个盒子就平白多出三份差额，换 `padding` 一样会影响尺寸。最后用 `outline` 画线，盒子仍按原来的尺寸参与排版。

### 4. 随手裁个圆角，开头的例子就演不出来了

给演示块加上 `overflow: hidden`，超出圆角的东西是裁干净了，三个盒子也突然肯缩了。原因还在那个自动最小尺寸：在这个横向示例里，`hidden` 属于可滚动的 overflow 值，主轴上的自动最小宽度会取 0。

在业务里这招有时碰巧合适。但如果只是希望子元素缩回去，直接给 `min-width: 0` 就好。`overflow: hidden` 会连溢出的内容一起裁掉。演示区要让人看见那半截 B，更不能顺手给它加上。

### 5. 同一份输入，复制出去却排成了另一种宽度

演示区分别设置 grow、shrink 和 basis，右栏为了方便复制，导出 `flex` 简写。比如输入一个没带单位的 `50`，导出就是 `flex: 2 3 50`。这条声明无效，在我的测试页上盒子回到 `0 1 auto`。演示区只有 `flex-basis: 50` 被丢掉，前两项还是 2 和 3。

我用真实 Chrome 测了 1000 个候选值。测试页里是 720px 宽的容器，单个盒子内容宽 80px。比较 `flex: 2 3 <值>` 和分开写的结果，大致是下面这样：

| 放进 basis 的值 | 简写 | 三项分开写 |
| :--- | :--- | :--- |
| `auto`、`0`、`100px`、`30%`、`2em`、`10vw`、合法的 `calc()` | 正常 | 正常 |
| `50`、`100pxx`、`-10px` | 整条无效 | basis 无效，grow 和 shrink 保留 |
| `initial`、`inherit`、`unset` | 不能和另外两个数拼成简写 | 全局关键字只作用于 basis |
| 取不到值又没写回退的 `var(--x)`、`env(x)` | 替换后整条失效 | 只影响 basis |

所以我给输入框留的范围比较保守，分享链接解码时也查一遍。少支持一种写法，最多是输入框不收；收进一个两边解释不同的值，别人从我这里复制出去的 CSS 就会排错。

### 6. 开了换行，先看你和浏览器分的是不是同一行

`flex-wrap: wrap` 时，浏览器按项目的外部假设主尺寸依次装行，连同 gap 一起算能不能放下。这个尺寸已经考虑了最小、最大尺寸的限制。所以在本站的例子里，一个被内容撑宽的盒子，可能比只看 basis 时提早换到下一行。`nowrap` 没有这一步，所有盒子都待在同一行。

在我测的随机换行场景里，只按 basis 分行，大约四成和浏览器不同。行里的成员已经换了，再拿两行的剩余空间互相对，怎么解释都是错的。我让叠加层和诊断跟着浏览器的实际分行走，再用盒子的位置核对。这样表里才说得清，究竟是谁缩不下去，又把旁边哪个盒子挤走了。

回到开头那张图，如果明细表只写着三个 120px，我大概会盯着 `flex-shrink: 1` 再查半天。有了旁边那列 58.7px，就知道该去翻最小宽度了。[todo-flex](https://huberyyang-space.github.io/todo-flex/) 会把你调好的布局记在地址栏里。下次碰到一行怎么也分不匀的盒子，可以直接把那一行发给同事，两个人对着同一组数看。[项目源码](https://github.com/HuberyYang-Space/todo-flex)
