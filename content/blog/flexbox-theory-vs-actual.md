一个 200px 宽的 flex 容器，里面放三个内容宽 120px 的盒子，`flex-shrink` 都是默认的 1。按规范一步步推导，每个盒子应该被压到 58.7px。浏览器实际给的是 120px，一个像素都没缩。

这不是浏览器的 bug，是 `min-width: auto` 在起作用。更有意思的是，我做的 Flexbox 演示站 [todo-flex](https://huberyyang-space.github.io/todo-flex/)，推导引擎故意不处理这条规则，就是为了让这 61.3px 的差额露出来。

如果你也被“`flex: 1` 怎么没等分”“子元素怎么把容器撑爆了”坑过，这篇会把浏览器算尺寸的过程摊开讲一遍，再讲 6 个测量浏览器时踩的坑。它们有一个共同点，都不报错。

## 「起因」

\[待填：你自己被 flex 尺寸坑过的一次真实经历，什么项目、什么现象、当时怎么查的\]

想找个工具把这件事看明白，翻了一圈发现，现有的 Flexbox 演示工具几乎都在演示对齐，`justify-content` 切一下，盒子往左挤、往右挤、两端散开。可开发里真正卡住人的，大多是尺寸侧的问题：

- `flex: 1` 为什么没把空间等分
- `min-width: auto` 为什么让子元素撑爆了容器
- `flex-basis: 0` 和 `auto` 到底差在哪

没有哪个工具告诉你，浏览器是怎么一步步算出那个宽度的。于是我花了一个月，提交了 141 次，做了 todo-flex。

## 「为什么要把理论值和实际值摆在一起」

站里每个盒子都同时显示两个数，理论值来自一套纯函数推导，实际值来自浏览器的真实渲染。三个具体原因：

1. **只看浏览器，你只知道它变成了什么样，不知道它本该是什么样。** 没有参照，就分不清哪部分是 grow / shrink 分配出来的，哪部分是别的规则改的。
2. **只看规范，你拿到的是理想值。** 手算对上了，不代表浏览器同意，浏览器还有 `min-width: auto`、换行这些规则在等着你。
3. **两边并排，差额本身就是信息。** 差多少、差在哪个盒子上，直接指向是哪条规则介入了。

反过来说，如果你只是想看 `justify-content` 的几个取值长什么样，MDN 或 Flexbox Froggy 更快，不必打开它。

## 「背景知识：flex 尺寸是怎么算出来的」

规范里这一段叫 Resolving Flexible Lengths（CSS Flexbox 规范 §9.7），写得很绕。拆开来其实就五步：

1. **定 basis**：`flex-basis: auto` 且没设宽度时取内容尺寸，百分比按容器主轴算。
2. **分行**：按 `order` 依次累加 basis 和 gap，放不下就换行（严格说累加的是被最小尺寸撑过的尺寸，闭坑指南最后一条会讲）。`nowrap` 时永远只有一行。
3. **算剩余空间**：容器主轴 − 所有 basis 之和 − 所有 gap 之和。
4. **分配**：剩余为正，按 `flex-grow` 的比例分出去；剩余为负，按 `flex-shrink × basis` 加权分摊溢出。
5. **冻结重分**：分摊后压到下限以下的盒子冻结在下限，溢出在其余盒子间重新分摊。

注意第 4 步的收缩是**加权**的，basis 大的盒子分摊得多。所以 `flex-shrink` 都是 1，也不代表大家缩一样多。

拿开头那个例子代进去（gap 是 12px）：

```text
剩余空间 = 200 − (120 + 120 + 120) − 2 × 12 = −184
每个盒子的收缩权重 = 1 × 120，三个一样
每个盒子分摊 = 184 ÷ 3 ≈ 61.3
理论最终 = 120 − 61.3 ≈ 58.7
```

站里选中任意一个盒子，“推导过程”页签就是这样一行行展开的，代入的数字照着算得出结果。

## 「故意不修的那道缝」

问题出在第 5 步的“下限”上。

flex 子元素的 `min-width` 默认值是 `auto`，它在主轴上的意思是**最小不能比内容最窄的时候还窄**（比如一段文字里最长的那个单词），规范里管这个下限叫自动最小尺寸。三个盒子的内容是 120px 宽的整块，一个像素都缩不动，浏览器只能让它们溢出容器。

我的推导引擎**故意不模拟这条规则**，它眼里的下限只有 0。

听起来像个偷懒的 bug。可你想想，如果引擎也把 `min-width: auto` 算进去，理论值和实际值都是 120px，明细表上就是两个一模一样的数字。读者看完只会觉得“哦，没缩”，至于为什么没缩，什么也学不到。

**一个什么都算对的推导引擎，在这里什么也教不了你。**

所以这道缝我留着，交给诊断层去解释。它逐个盒子比对理论值和实际值，发现实际值比理论大、而且正好停在内容尺寸上，就会直接说：

```text
⚠ min-width:auto 撑住了内容固有尺寸，收缩到此为止
```

\[待填：配图，陷阱场景下明细表与诊断的截图\]

还不止这一种情况。同一行里有盒子被 `min-width: auto` 兜住、多占了空间，它旁边的盒子就会被挤得比理论更小，这时诊断会点名源头是哪个盒子。换行位置被撑宽的盒子改变了，也会单独说明。归不到已知规则的差异，它也不硬猜，如实说没能归因。

差额不是误差，是线索。

这套设计成立有一个前提，**实际值那一侧必须真的是浏览器排出来的**。所以演示区是真实 DOM 加真实 CSS flex 渲染，没有用 JS 去算盒子位置。也正因为这样，右栏导出的那段 CSS 复制进项目，是真能复现出演示区的。

## 「闭坑指南」

要让“实际值”可信，先得把浏览器测准。这部分花的时间比推导引擎还多，下面 6 个坑，每一个都不报错，只会让数字悄悄变错。

\[待填：这些坑当时是怎么发现的，挑一两个讲讲现场\]

::warning{title="getBoundingClientRect 读到的是动画中间态"}
盒子位置变化用 GSAP Flip 做过渡，Flip 靠 `transform` 把盒子从旧位置平滑挪到新位置。`getBoundingClientRect()` 返回的矩形是算上 `transform` 的，过渡期间去读，拿到的是动画走到一半的位置和大小，明细表里的数字就跟着乱跳。做法：尺寸读计算样式，位置读 `offsetLeft` / `offsetTop`，这两者都不受 `transform` 影响。`ResizeObserver` 只当触发器用，通知该重新采样了，不从它身上读尺寸。
::

::warning{title="offsetWidth 会取整，差出的 0.5px 刚好撞上容差"}
既然 `offsetWidth` 也不受 `transform` 影响，为什么不用它？因为它返回整数。flex 分出来的尺寸经常带小数（比如开头的 58.67px），取整最多差出 0.5px。而诊断层判定“理论和实际不一致”的容差正好是 0.5px，用来吸收亚像素舍入的噪声。取整误差一撞上这条线，就会凭空报出“有规则介入”。所以尺寸一律读计算样式里带小数的值。
::

::warning{title="描边用 border 或 padding，会被当成规则介入"}
给演示块加个描边，最顺手的写法是 `border`。但 `border` 和 `padding` 都占布局空间，每个盒子的实际尺寸都比推导多出一圈，诊断层会把这个恒定偏差当成规则介入，全量误报。更糟的是，导出的 CSS 里没有这圈装饰，复制到项目里排出来的结果和演示区对不上。做法：描边一律用 `outline`，它不占布局空间。
::

::caution{title="overflow: hidden 会让 min-width: auto 悄悄失效"}
自动最小尺寸只在盒子不是滚动容器时生效，而 `overflow: hidden` 恰好会把它变成滚动容器。给盒子加上这一句（比如想裁掉圆角外的内容），`min-width: auto` 就退化成 0，盒子可以一路缩到底。页面看起来完全正常，只是这个站最想演示的那个陷阱，再也复现不出来了。反过来说，这也是为什么你在项目里遇到子元素撑爆容器，“加个 `overflow: hidden` 就好了”。
::

::warning{title="flex 简写和单项属性，对同一个 basis 的态度不一样"}
演示区用 `flex-grow` / `flex-shrink` / `flex-basis` 三条单项属性渲染，右栏导出的是 `flex` 简写。我在真实 Chrome 里拿 1000 个候选值逐个对比，发现两者对一部分 basis 值的处理完全不同。`flex: 2 3 50` 整条声明作废，盒子退回 `0 1 auto`；`flex-basis: 50` 却只丢掉 basis 这一项，grow 和 shrink 照样生效。同一个输入，演示区和导出的 CSS 排出两种结果，两边都不报错。
::

分歧的范围比想象中大，挑主要的几类列在这里（720px 容器里一个内容 80px 的盒子，`flex: 2 3 <值>` 对比三条单项属性）：

| 写法 | 例子 | `flex` 简写 | 单项属性 |
| :--- | :--- | :--- | :--- |
| 关键字、长度、百分比、运行期单位、数学函数 | `auto` `0` `100px` `30%` `2em` `10vw` `calc()` | 正常 | 正常，两边一致 |
| 没带单位的非 0 数、拼错的值、负值 | `50` `100pxx` `-10px` | 整条失效 | 只丢 basis |
| CSS 全局关键字 | `initial` `inherit` `unset` | 整条失效 | 只丢 basis |
| 没有回退值的 `var()` / `env()` | `var(--x)` | 计算期整条失效 | 只丢 basis |

所以站里的 basis 输入框只收**确定合法**的写法，拿不准就拒，分享链接解码也走同一道关。错拒只少一种写法，错收会让导出的 CSS 整条失效，两害相权，宁可保守。

::warning{title="浏览器按撑宽后的尺寸断行，不按 basis"}
开了 `flex-wrap: wrap` 之后，浏览器决定一个盒子放在哪一行，用的不是 basis，而是 basis 和内容尺寸取大之后的假设尺寸。推导引擎如果照着 basis 断行，随机换行的场景里大约四成跟浏览器不一样，断行一错，后面的分配就全错了。做法：叠加层和诊断改成按浏览器实际断行分组，几何位置只用来核对两边有没有矛盾。
::

这 6 个坑串起来是同一个教训：**测量工具给出的假结论，比没有结论更危险。** 没有结论你会继续查，假结论会让你放心地往下写。

## 「FAQ」

**`min-width: 0` 和 `overflow: hidden` 都能解决子元素撑爆，选哪个？**
两者都让自动最小尺寸失效，区别在副作用。`overflow: hidden` 会裁掉超出的内容，还会让元素变成滚动容器；`min-width: 0` 只改最小尺寸，不动别的。只想让盒子能缩，用 `min-width: 0`；本来就想裁掉溢出内容，再用 `overflow`。主轴是纵向（`flex-direction: column`）时，对应的是 `min-height`。

**`flex: 1` 为什么没有等分？**
`flex: 1` 等于 `flex: 1 1 0%`，basis 是 0，所有空间都按 grow 均分，理论上就是等分的。没等分，通常是某个盒子的内容比它分到的宽度还宽，被 `min-width: auto` 撑住了，其余盒子只能分剩下的那部分。

**`flex: 1` 和 `flex: auto` 差在哪？**
`flex: auto` 等于 `flex: 1 1 auto`，basis 取内容尺寸，先按内容各自占位，再把剩余空间按 grow 分，所以内容多的盒子最后更宽。`flex: 1` 的 basis 是 0，跳过了按内容占位这一步。

**为什么不直接用 JS 把盒子位置算出来画？**
那样“实际值”就成了第二份理论值，两边永远对得上，这道缝也就消失了。导出的 CSS 也不再保证复制进项目能复现，因为演示区根本不是 CSS 排出来的。
